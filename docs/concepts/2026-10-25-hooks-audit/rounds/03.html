Was ersetzt graphify? — Recherche (offizielle Doku, Studie, Community)

  • Anthropic setzt bewusst auf Suche statt Index. Claude Code holt Dateien „just in time“ über Grep, Glob und Read und lädt vorab nur eine kleine CLAUDE.md (Engineering-Blog). Die Best Practices nennen „file-by-file descriptions of the codebase“ ausdrücklich als etwas, das nicht in CLAUDE.md gehört (Doku). Einen eingebauten Index gibt es nicht: Der Wunsch danach wurde als „not planned“ geschlossen.
  • Die einzige kontrollierte Studie (AGENTS.md-Studie, Feb. 2026) fand, dass Repo-Übersichten Agents nicht schneller zur richtigen Datei bringen. Generierte Übersichten kosteten +20 % Tokens.
  • Die großen Spar-Zahlen graph-basierter Tools (5–10×, 99 %) stammen von Herstellern oder aus Anekdoten und werden gegen ein schwaches Grep verglichen. Das typische Muster in der Community: Das Modell ruft das Tool kaum auf. Genau das zeigen auch deine Zahlen (4 Abfragen in 25 Tagen).
  • Was wirkt und offiziell empfohlen ist: breite Erkundung an einen Haiku-Subagent auslagern (scout), damit die gelesenen Dateien nicht im Hauptkontext landen. Für typisierte Sprachen kommt das offizielle LSP-Plugin dazu (Referenzen und Symbole ohne Index).

Fazit: Deine Grundidee, ein „Inhaltsverzeichnis statt alles hochladen“, erfüllt heute die kleine project-map.md (1–2 KB, einmal pro Session, nur auf Bedarf) zusammen mit scout. Mehr Karte bringt laut Studie nichts. Ich würde nur ihre generischen Ordner-Hinweise durch echte Projekt-Hinweise ersetzen und die Block-Meldung des tokens.guard auf scout zeigen lassen.

auto-fix — wirkt er, wird er getriggert?

Seit 1. Oktober (alle Desktop-Sessions, 3.639 Prompts):

  • 133 Prompts klangen nach Fehlern („geht nicht“, „Fehler“, „broken“ …). Bei keinem wurde auto-fix geladen.
  • Insgesamt wurde er dreimal geladen: zweimal, weil du „/auto-fix“ im Text geschrieben hast, einmal von Claude selbst. Jeder Lauf brauchte 50–63 Tool-Calls.
  • Der automatische Trigger über die Skill-Beschreibung greift also praktisch nie. Bei 3 Läufen lässt sich nicht sagen, ob er besser ist als direktes Fixen.

Vorschlag: Ein A/B-Eval mit 4–6 echten Bug-Fällen aus diesen Sessions, je mit und ohne Skill. Gewinnt der Skill (weniger Calls, gleiche oder bessere Lösung), bekommt er einen Trigger, der wirklich greift. Gewinnt er nicht, wird er auf „nur auf Zuruf“ verschlankt und die Auto-Trigger-Versprechen fliegen aus der Beschreibung.

PR D · Notiz-Pins in Dokument- und Report-Runden

Die Annotation-Ebene der Concept-Engine bekommt einen Dokument-Modus: Strg+Klick (auf Touch langes Drücken) setzt eine eigene Notiz an einen Absatz oder eine Tabellenzeile. Das Anhängen von Dateien, das Eye-Toggle und die Alt-Hinweise funktionieren wie in Design-Runden. Die Notizen kommen als userPins im Payload an und werden beim Einfrieren mit übernommen. Wirkt erst für künftige Concepts, wie von dir gewünscht.

PR E · Dispatcher pro Event

Pro Event startet nur noch ein Node-Prozess. Er lädt die Module des Events und ruft sie nacheinander auf, jedes mit try/catch und eigenem Zeitbudget, und führt die Ausgaben zusammen. Damit sinkt die Zahl der Prozessstarts pro Bash-Call von 17 auf 2. Der Nachweis kommt aus der Telemetrie von PR A (Dauer, Timeouts, Spawns vorher und nachher).

PR F · MCP-Server schlanker

Zuerst wird gemessen, wie viel RAM jeder der drei Server beim Start belegt und welche Module er dafür lädt. Danach gibt es zwei Wege: Lazy-Requires, bei denen die Tool-Namen gleich bleiben, oder ein gemeinsamer Server, der die Tool-Präfixe ändert und alle Verweise mitziehen muss. Die Wahl lege ich dir mit den Messwerten vor, bevor gebaut wird. Das ist der einzige Punkt, an dem die Umsetzung noch einmal nachfragt.
