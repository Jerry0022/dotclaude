Repo-Mode für Nicht-Git-Projekte

devops-Plugin v0.135.1 · Befundlage & Strategieentscheidung

Iteration 1 · Befunde und Grundsatzentscheidung

Drei Agents (Audit, Red-Team, Product Owner) plus eigene Reproduktion. Der Audit hat 28 Hooks und die ship-Tools in eigens gebauten Test-Repos ausgeführt — die Ausgaben unten sind echt, nicht geschätzt. Neun Befunde, davon zwei mit Schreibzugriff außerhalb des gemeinten Ziels und einer, der Arbeiten komplett unmöglich macht. Die Grundsatzfrage steht weiter unten: degraded oder supported.

Ist-Zustand — was heute wirklich passiert

Die ursprüngliche Idee war: beim ersten Mal fragen, ob das Projekt ein Git-Projekt werden soll, Entscheidung speichern, in Hooks und Skills berücksichtigen. Die Recherche hat das Bild verschoben.

Der Detektor existiert seit v0.73.0. Commit 9761a08 „feat(non-vcs): repo-mode + guards + delivery docs (0.73.0) (#150)" hat genau dieses Feature gebaut — inklusive drei Zuständen none / git-no-remote / git. Wir sind heute bei v0.135.1. Das Feature ist in 62 Minor-Versionen still verrottet: die Card-Verdrahtung wurde durch Schema-Drift gekappt, die Skill-Gates sind im De-Prefix-Refactor verschwunden. Nichts ist laut kaputtgegangen, weil nichts es getestet hat.

Der wichtigste Befund der Inventur: git-no-remote ist schlimmer als none. Mode none ist an den meisten Git-Eintrittspunkten abgefangen. git-no-remote kommt durch jeden is-inside-work-tree-Guard durch und scheitert erst am Remote — dort, wo niemand mehr prüft.

Korrektur zu meiner ersten Einschätzung: ich hatte behauptet, die Hooks seien bereits alle still. Das war doppelt falsch — es sind vier Hook-Blocker, nicht einer, und der schwerste liegt nicht in none, sondern in git-no-remote.

Sauberes Vorbild im eigenen Haus: ss.git.sync.js:41-42 und stop.git.sync.js:57-58 haben als einzige den korrekten Doppel-Guard — Repo und Remote. Das ist das Muster, das der Rest kopieren sollte.

F7 — Totale Arbeitsblockade in lokalen Repos ohne Remote schwerster Befund Audit, ausgeführt

In einem Repo mit git init + Commits, aber ohne Remote, auf main: Claude kann weder eine Datei editieren noch einen schreibenden Git-Befehl absetzen. Beide Guards prüfen isGitRepo(), aber keiner prüft, ob ein Remote existiert.

pre.main.guard.js:86,96   → Exit 2
  BLOCKED: Write operation on local 'main' is not allowed.
  Fix: git fetch origin && git switch -c <feat/topic> origin/main

pre.edit.branch.js:102,115 → Exit 2 (schon bei einem simplen Edit)
  BLOCKED: Editing files on local 'main' is not allowed.
Der ausgegebene Ausweg existiert nicht. Beides verifiziert:
git fetch origin → fatal: 'origin' does not appear to be a git repository
git switch -c feat/topic origin/main → fatal: invalid reference: origin/main
Der einzige funktionierende Ausweg ist DEVOPS_ALLOW_MAIN=1 — im Text nur als Notnagel erwähnt.

Das ist die Sackgasse, aus der ein Nutzer sich ohne Kenntnis der Plugin-Interna nicht befreien kann: die Fehlermeldung nennt einen Fix, der garantiert scheitert. Fix ist klein — Remote-Check ergänzen, und ohne Remote entweder überspringen oder den Text auf git switch -c <feat/topic> ändern.

F8 — AFK-Skills schreiben in den Dateisystem-Root destruktiv Audit, reproduziert

Drei Skills benutzen dasselbe Idiom, um Pfade in .git/info/exclude einzutragen:

x="$(git rev-parse --path-format=absolute --git-common-dir)/info/exclude"
mkdir -p "$(dirname "$x")"
Ohne Git kollabiert die Kommandosubstitution zu einem Leerstring:
resolved x = [/info/exclude] · mkdir -p target = [/info]
Also mkdir -p /info plus Append — außerhalb des Projekts, im Wurzelverzeichnis.

Betroffen: run-autonomous/SKILL.md:269-271, run-backlog/SKILL.md:227-233, claude-batch/SKILL.md:105-108. run-autonomous:275 hat Prosa-Schadensbegrenzung über das Ergebnis — der Shell-Block läuft trotzdem. Die anderen zwei haben gar nichts.

Besonders unangenehm: zwei davon sind die unbeaufsichtigten AFK-Runner. Der Fehler passiert, während niemand hinschaut.

F4 — Ancestor-Erkennung schreibt in ein fremdes Repo destruktiv selbst reproduziert

detectRepoMode() fragt git rev-parse --is-inside-work-tree. Das ist vorfahrenbewusst: liegt das Projekt irgendwo unterhalb eines Git-Repos — Home-Dotfiles, Monorepo-Checkout, ein versehentliches git init zwei Ebenen höher — meldet es Erfolg. Das Nicht-Git-Projekt wird als git klassifiziert, mit toplevel auf dem Vorfahren.

Reproduktion: git init outer, darin outer/sub/notgit anlegen, dort rev-parse --is-inside-work-tree → Erfolg, --show-toplevel → …/outer.

ship_cleanup ist das einzige ship-Tool ganz ohne Repo-Mode-Gate — preflight, release und version-bump haben eines, cleanup nicht. Es führt aus:

cleanup.js:71   gitStrict(`checkout ${base}`, opts)
cleanup.js:90   gitStrict(`pull --ff-only origin ${base}`, {...opts, timeout: NETWORK_TIMEOUT})

— im Repo des Vorfahren, das der Nutzer nie gemeint hat. Plus Branch-Löschung. Auf Windows ist „Projekt unter einem Home-Repo" kein Randfall.

Fix zieht

  • Ein zusätzlicher Modus git-foreign-root: --show-toplevel gegen die Session-Wurzel vergleichen
  • Repo-Mode-Gate in cleanup.js nachziehen — die anderen drei Tools haben es bereits

Wenn nicht gefixt

  • Bleibt ein stiller Schreibzugriff auf ein fremdes Repo
  • Wird durch „ein Detektor für alles" repo-weit zementiert statt behoben

F1 — Falschmeldung „Detached HEAD" bei jedem Session-Start Blocker selbst reproduziert

checkWorkspace() kann „kein Branch, weil detached" nicht von „kein Branch, weil kein Repo" unterscheiden. currentBranch() gibt in beiden Fällen null zurück, und der if (!branch)-Zweig meldet hohe Severity.

Reproduktion (Hook in leerem Temp-Ordner ausgeführt):
⚠ Detached HEAD in repo root (not in a worktree) — commits will not belong to any branch
plus „Call AskUserQuestion as the FIRST action of this turn". Exit 0.

Das ist die einzige der zehn Git-Hooks ohne Repo-Guard. Alle anderen haben ihn bereits — pre.main.guard.js:86 macht exakt if (!isGitRepo(cwd)) process.exit(0). Es fehlt eine Zeile, kein Subsystem.

Dafür

  • Größter Schmerzanteil, kleinster Fix
  • Kaputt ist eine selbstbewusste Falschaussage, nicht ein stilles Nichts
  • Kapert zusätzlich den ersten Zug jeder Session mit einer Rückfrage

Dagegen

  • Keine — reine Regressionsreparatur

F2 — Der file-only-Pfad der Completion Card ist toter Code Blocker selbst verifiziert

Deine Beobachtung („die Card landet auf ship-blocked") trifft ein echtes Problem, aber die Ursache liegt eine Ebene tiefer: die Card kann den file-only-Zustand gar nicht empfangen.

Zwei unabhängige Brüche, beide nachgeprüft:
1. index.js:398-406 rendert eine file-only-Statuszeile, abhängig von state.mode. Das zod-Schema für state (index.js:1206) kennt nur branch, worktree, commit, pushed, pr, merged, appStatus, kept, deployPending. Zod entfernt unbekannte Keys — state.mode kommt nie an. Zweig unerreichbar.
2. index.js:267 definiert die Variante ready-files. Das Varianten-Enum (index.js:1183) listet sie nicht. Einzige Fundstelle im ganzen Repo. Ebenfalls unerreichbar.

Zusätzlich rät variant-guard.js beim Downgrade dazu, state:{pushed:true, merged:"<base>"} mitzugeben — ein Rat, der in einem Repo ohne Remote nicht befolgbar ist.

Der Audit hat es schlimmer gefunden als „toter Code". Er hat die Card über den echten MCP-Server in einem Nicht-Git-Ordner gerendert:

> ➖ up-to-date origin/main · uncommitted        (variant: ready)
> ➖ up-to-date origin/main · uncommitted        (variant: analysis, state {})
## 🚀 SHIPPED. merged → origin/main — All DONE   (variant: ship-successful)

Die Card behauptet, ein Remote-Branch sei aktuell — in einem Verzeichnis ganz ohne .git. Der else-Zweig in index.js:478-480 feuert das sogar bei leerem state:{}, also trägt jede Card in einem Nicht-Git-Projekt eine falsche origin-Aussage. Und nichts hindert eine ship-successful-Card daran, dort einen Merge zu behaupten.

Deine Beobachtung war also nicht nur richtig, sondern untertrieben: es ist nicht bloß die falsche Variante, es ist eine erfundene Remote-Aussage.

Dafür

  • ~6 Zeilen: Schema erweitern, Enum ergänzen, Guard bei file-only aussetzen
  • Der Rendering-Code existiert bereits und ist ungetestet, aber geschrieben

Offene Frage

  • War die Trennung irgendwann Absicht? Dann wird hier eine geschlossene Entscheidung neu aufgemacht

F5 — ship_release meldet Erfolg, lässt aber Änderungen uncommitted Blocker selbst verifiziert

release.js:49  const repoMode = detectRepoMode(cwd)
release.js:50  if (repoMode === "none")           return { success: true, skipped: true, reason: "file-only-mode" }
release.js:53  if (repoMode === "git-no-remote")  return { success: true, skipped: true, reason: "no-remote" }
               // ↓ nie erreicht: Konfliktmarker-Scan, Version-Commit, CHANGELOG

In git-no-remote ist das besonders falsch: das Repo kann committen, es hat nur kein Remote. Version-Bump und CHANGELOG-Edits früherer Schritte bleiben liegen, während die Pipeline Erfolg meldet und die Card auf ready herunterstuft — was für den Nutzer wie „fertig" aussieht.

Vom Audit real durchgespielt:
dirty before: M package.json · HEAD before: acc6108
→ {"success":true,"skipped":true,"reason":"no-remote","delivered":"local-commit-only"}
HEAD after: acc6108 (unverändert) · dirty after: M package.json
Das Feld delivered:"local-commit-only" ist damit schlicht gelogen — es wurde nichts committed.

Und die Kette geht weiter: skills/ship/SKILL.md:442 sagt „After ship_release returns success: true and merged: 'main'…". success ist true, merged ist undefined — der Nutzer bekommt gemeldet, seine Arbeit sei nach main geshippt, während nichts die Maschine verlassen hat. Der dokumentierte Rückgabetyp bei SKILL.md:371-374 stimmt ebenfalls nicht mit der echten skipped-Form überein.

Zwei saubere Auswege

  • git-no-remote bekommt einen echten Local-Commit-Pfad
  • oder /ship verweigert ehrlich statt Erfolg zu melden

Risiko

  • Ein binäres Git/Kein-Git-Modell hat für diesen Zustand keinen Platz
  • git-no-remote ist der häufigere Fall als none

F3 — skills/ship/SKILL.md hat keinen file-only-Zweig degradiert Agent-Befund

Die Tool-Schicht ist angepasst, die Skill-Schicht nicht. preflight liefert korrekt ready:true, mode:"file-only", branch:"<file-only>" — und der Skill liest mode nie. Schritt 1a wertet autoDetectedBase, intermediate und outOfBandDeploys aus, dann marschiert er in Codex-Review, Rebase, Push, PR, Merge.

Einzige file-only-Fundstelle im ganzen Skill: Zeile 261, ein Purpose-Alignment-Skip. Das ist das eigentliche Ship-Versagen — eine Datei, nicht fünf bis acht.

Namenskollision beachten: ein „Step 0 — Repo-Mode" geht nicht, SKILL.md:107 hat bereits „Step 0 — Load Extensions".

F9 — Ein kopierter Branch-Block bricht sechs Agents Blocker Audit

ai.md, core.md, frontend.md, windows.md, designer.md und feature.md tragen einen byteidentischen Block „Branch Setup (mandatory first step)":

git fetch origin && git reset --hard origin/<parent_branch>   # beide Modi fatal
git checkout -b <parent_branch>/<role>                        # mode none fatal

feature.md ist der schlimmste Fall: es propagiert einen nicht existierenden Parent branch: in jeden Sub-Agent, der dann denselben scheiternden git reset --hard origin/<that> ausführt — Kaskadenfehler. Und feature.md:92-93 zwingt über FEATURE_RESULT: branch/commits erfundene Werte zurück in den Orchestrator.

Gute Nachricht: ein einziger geguardeter Rewrite patcht alle sechs Dateien, weil der Block überall identisch ist.

F6 — Der Test, der die zweite Verrottung verhindert höchster Langzeitwert

#150 hat dieses Feature schon einmal gebaut. Es ist still gestorben, weil kein Test es gehalten hat. Ohne diesen Punkt verrottet auch die jetzige Reparatur — die Frage ist nur, bis welcher Version.

Zwei Tests, klein:

  • Jeden SessionStart- und UserPromptSubmit-Hook in einem leeren Temp-Ordner und in einem git init-ohne-Remote-Ordner ausführen, leeres stdout erwarten
  • Card-Test: mode:'file-only' überlebt das Schema und rendert ready-files

Weitere Lücken, die der Red-Team-Durchgang benannt hat: Nicht-Git-Ordner unter einem Git-Repo (F4), Bare-Repo, cwd innerhalb .git, gesetztes GIT_DIR, sowie ein voller /ship in beiden Zwischenzuständen mit der Zusicherung, dass die Pipeline nicht Erfolg meldet, solange Version/CHANGELOG noch im Working Tree liegen.

Deine Idee A — Entscheidung in .claude/repo.json speichern beide Agents dagegen

Beide Agents empfehlen unabhängig, das nicht zu bauen. Die Gegenargumente, geordnet:

Dafür spricht

  • Konsistent mit dem vorhandenen Consent-Muster (graphify-state.js)
  • Unterdrückt Wiederholungsfragen

Dagegen spricht

  • repo-mode.js:3-4 verwirft explizit sogar einen In-Memory-Cache: „staleness is the bigger risk". Eine Datei auf Platte ist strikt schlechter
  • Kein Zuhause: in einem Nicht-Git-Projekt ist es eine untracked lokale Datei ohne Backup — ausgerechnet ihr Zweck ist Persistenz
  • Schlüsselt auf rohem cwd → jeder Worktree und jedes Unterverzeichnis bekommt einen eigenen Datensatz, die Unterdrückung konvergiert nie
  • check-claude-artifacts.js:24-45 bricht den Build, wenn eine neue projektwurzel-.claude/-Datei nicht registriert ist
  • Getrackt wandert die Aussage „ist kein Git-Projekt" in jeden Clone, wo sie falsch ist
  • Global gespiegelt bedeutet es „nirgends auf dieser Maschine Git anbieten" — semantisch etwas völlig anderes als bei graphify
  • Einziger Konsument ist Nag-Unterdrückung — und run-once.js kann das bereits per Cooldown ohne jede Persistenz

Die Regel „Live-Erkennung gewinnt immer" ist Konvention, kein Enforcement. Sobald die Lib einen Reader exportiert, liest ihn irgendwann jemand als Wahrheit — und nichts schlägt fehl, wenn er es tut.

Deine Idee B — beim ersten Mal fragen (bzw. lazy fragen) Deadlock in autonomen Skills

Ich hatte im ersten Durchgang vorgeschlagen, die Frage von SessionStart auf „lazy, erst wenn Git gebraucht wird" zu verschieben. Das Red-Team hat den Vorschlag zerlegt:

Dafür

  • Frage erscheint dort, wo sie relevant ist

Dagegen

  • run-autonomous/SKILL.md:428-432 verbietet jede AskUserQuestion nach der Freigabe; run-backlog ist die ship-Instanz, die AFK läuft. Der Lazy-Prompt blockiert die Schleife — oder das Modell antwortet stellvertretend und schreibt eine Entscheidung fest, die niemand getroffen hat
  • Verletzt die Invariante aus #268 („ein Befund wird nie an die Rückfrage gekoppelt", git-check-output.js:9-24)
  • Das Plugin verhandelt eine bewusste Nutzerentscheidung neu: wer kein Git will, hat kein git init getippt
  • graphify hat dieselbe Abwägung schon getroffen — ss.graphify.js:128 sagt wörtlich „Not an offer"

Falls überhaupt: eine gedrosselte Transparenzzeile ohne Rückfrage, und niemals ein Schreibvorgang aus einem nicht-interaktiven Pfad.

Deine Idee C — Repo-Mode-Gate in alle Git-abhängigen Skills auf einen Skill eindampfen

Korrektur meiner Zahl aus dem ersten Durchgang: das Plugin hat 21 Skills, nicht 67 (67 sind Dateien unter skills/ inklusive deep-knowledge). Von den 21 führt genau einer eine mehrstufige Git-Pipeline aus, die ohne Git lügt: ship.

Das Trennkriterium: ein Skill braucht ein Gate nur, wenn er ohne eines eine Falschaussage erzeugt oder etwas zerstört. Alles andere scheitert laut und lesbar („not a git repository") — der Nutzer versteht es sofort, nichts wird zerstört.

Bereits gegated9 Git-Hooksnichts tun

Und: Prosa ist kein Enforcement. Genau die Skill-Gates aus #150 sind im De-Prefix-Refactor d3e9b6b verdunstet. Das billigste echte Enforcement ist die Tool-Grenze — jeder ship_*-Handler bekommt bereits cwd, drei rufen den Detektor schon auf. cleanup.js nachziehen wirkt mehr als jeder Markdown-Absatz.

Idee D — ein Detektor über Hooks (CJS) und MCP-Server (ESM) umstritten

Hier widersprechen sich die Agents, deshalb steht es als eigene Entscheidung.

Red-Team: Teil 1 ist tragfähig

  • Sollte allein ausgeliefert werden — mit F4, Timeout und Vokabular-Fix
  • Beseitigt zwei stille Vertragsbrüche: Hooks vergleichen stdout === 'true', repo-mode.js prüft nur den Exit-Code → in einem Bare-Repo oder innerhalb .git kippt das Verhalten von „überspringen" auf „ausführen"
  • Beendet die Doppel-Vokabular-Falle: der Detektor sagt none, preflight benennt es in file-only um — ein Prosa-Vergleich gegen das falsche Token feuert nie und scheitert offen

PO: nicht als Voraussetzung verkaufen

  • Vier Hook-Kopien à ~6 Zeilen; ein Dual-Format-Shim hat mehr bewegliche Teile als die Duplikation
  • repo-mode.js hat kein Timeout und bewusst keinen Cache — im Hook-Pfad (feuert bei jedem Bash-Write) blockiert ein hängendes Netzlaufwerk die Session; jeder existierende Hook-Detektor setzt eines (ss.graphify.js:103 = 4000 ms)
  • Eine fünfte Kopie in ss.git.check.js löst F1 sofort

Auflösung: beide haben in ihrem Teil recht. Kurzfristig eine Kopie für F1; die Konsolidierung ist eine eigene, saubere Aufräumarbeit — kein Türsteher vor den Fixes.

★ Die eine Entscheidung, die alles andere bestimmt

Ist file-only ein unterstützter Modus oder ein degradierter Modus? Alles Weitere folgt daraus mechanisch. Wähle unten genau eine Variante — die andere auf „Verwerfen".

Variante A — Degraded Mode Empfehlung beider Agents

Das Plugin ist in einem Nicht-Git-Projekt still, ehrlich und nicht-destruktiv — und verspricht nicht mehr. Die Akzeptanzschwelle lautet: lügt es, oder zerstört es etwas? Nicht: funktioniert das Feature in beiden Modi?

Dafür

  • Das „unterstützt"-Versprechen ist ohnehin nicht haltbar: ohne Remote gibt es keinen PR, keinen Merge, kein Tag, kein Rollback. Ein „Ship" in file-only ist ein cp
  • Der Beweis liegt im Repo: #150 hat „supported" gewählt, das Versprechen verfiel in unter 60 Minors — gemessen, nicht geschätzt
  • Begrenzt den langen Schwanz dauerhaft per Politik statt per Feature-Matrix
  • Macht den P0-Schnitt selbsterklärend richtig

Dagegen / Konsequenz

  • /setup-issue, /promote, /setup-cleanup scheitern weiterhin — laut, aber sie scheitern
  • Konsequent zu Ende gedacht steht auch preflight.js:45 auf der falschen Seite: ein synthetischer Commit-Hash ist kosmetische Fiktion. Degraded heißt — rendern, keinen Fake-Hash

Variante B — Supported Mode deine Ursprungsidee, vollständig

File-only wird ein erstklassiger Modus: Erkennung, persistierte Entscheidung, Prompt, Gates in Skills, eigener Ship-Pfad, eigene Card-Variante, dauerhafte Zwei-Wege-Testmatrix.

Dafür

  • Nutzer in Nicht-Git-Projekten bekommen eine durchgängige Story statt Sackgassen
  • Der Fall ist real und stabil — #150 entstand aus einem echten, dauerhaft nicht-versionierten Verzeichnis

Dagegen

  • Investiert in die ~20 % des Produkts, die in solchen Projekten überhaupt funktionieren
  • Jedes künftige Git-Feature bekommt dauerhaft einen zweiten Codepfad plus zweite Testmatrix
  • Genau dieser Weg wurde einmal gegangen und ist unbemerkt verfallen

Variante C — Minimalschnitt: nur Blockade und Fremdschreibzugriffe

Nur die Positionen 1–3 der Reihenfolge unten: F7 (totale Blockade), F8 (Schreiben in den Dateisystem-Root) und F4 (Schreiben ins fremde Repo). Card, Ship-Skill, Release und ss.git.check bleiben, wie sie sind.

Dafür

  • Drei kleine, risikoarme Änderungen
  • Beseitigt genau das, was Arbeit verhindert oder außerhalb des Ziels schreibt
  • Erfordert keine Grundsatzentscheidung — funktioniert unter A wie unter B

Dagegen

  • Deine konkrete Beschwerde — die Card nach dem Ship — bleibt ungelöst
  • F5 bleibt: Erfolgsmeldung mit uncommitteten Änderungen, plus die Merge-Behauptung in SKILL.md:442
  • F1 bleibt: Falschmeldung bei jedem Session-Start

Empfehlung und Reihenfolge

Variante A (Degraded Mode) als Politik — aber der Befundstapel ist größer als die Grundsatzfrage. Deine drei Ursprungsideen (repo.json, Prompt, Skill-Gates) fallen weg; nicht weil die Idee schlecht war, sondern weil die Recherche zwei Dinge zeigt: der Detektor ist seit v0.73.0 da, und das eigentliche Problem heißt Verrottung plus fehlender Remote-Check, nicht fehlende Erkennung.

Der Punkt, an dem deine Ausgangsfrage sich gedreht hat: du hast gefragt, ob man Nicht-Git-Projekte erkennen und die Entscheidung speichern kann. Die Antwort ist ja — aber das Speichern löst nichts. Was tatsächlich weh tut, sind zehn konkrete Stellen, an denen das Plugin ohne Remote lügt, blockiert oder außerhalb des Projekts schreibt.

Abschlussbericht · Repo-Mode umgesetzt

Alle neun Befunde implementiert, Variante A (Degraded Mode) als Politik — mit deiner Einschränkung, dass /ship in file-only alles ausführt, was keine Git-Aktion ist.

Zusammenfassung

Die Grundsatzfrage ist als Degraded Mode beantwortet, aber nicht als „Plugin schweigt und tut nichts". Dein Kommentar hat den file-only-Ship-Pfad neu definiert: Build, Tests, Doku-Frische und Quality-Gates laufen weiter, nur Push/PR/Merge entfallen — und das Ergebnis wird ehrlich berichtet statt als Merge ausgegeben.

Die vier Ursprungsideen sind verworfen und nicht gebaut: kein .claude/repo.json, kein Erst- oder Lazy-Prompt, keine Prosa-Gates über mehrere Skills, kein Dual-Format-Detektor. Der Detektor existierte bereits seit v0.73.0 — er war nur ungenau und ungetestet.

Nicht durch diese Arbeit verursacht und bewusst nicht mitgefixt — aber ein Flake ist ein eigener Defekt, deshalb steht er unten als Issue-Kandidat.
